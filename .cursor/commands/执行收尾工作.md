# 执行收尾工作

对本仓库执行一次**文档与代码注释收尾**：全面更新文档、代码注释，清理过时、错误、冲突的内容，保证文档、代码注释与当前实现一致。

命令后若附带范围或限制（例如「只做文档」「先不跑全量测试」），以附加要求为准；未指定则按本提示词全仓执行。

## 目标与边界

**要做**：

- 以当前代码、构建脚本、测试注册为事实源，校正所有描述性文档与代码注释。
- 删除或改写过时内容：旧版本号、已改名/删除的文件与符号、已下线特性、失效链接、过期示例。
- 消除重复与冲突：同一事实只保留一个权威出处，其余改为交叉引用。
- 区分「规范目标」与「当前实现」：规范可以领先实现，但必须显式标注「待落地／未实现」，不得把未实现说成已实现，也不得为了迁就实现而下调规范。

**不要做**：

- 不改变运行语义，不顺手重构代码，不修与本任务无关的 bug。
- 不重写历史记录（CHANGELOG、审计报告、整改台账的既成条目）；历史只追加或加「已由 …… 取代」注记。
- 不删除用户未提交的改动，不批量删除无法确认用途的文件。
- 不编造事实；无法核实的内容留给「遗留问题」清单。
- 不提交构建产物、覆盖率数据、临时文件。
- 提交信息不加 Cursor `Co-authored-by` trailer（见 `.cursor/rules/git-commit.mdc`）。

## 事实优先级（冲突时按此裁决）

1. **实际行为**：`src/` 代码 + `tests/` 用例 + 构建/测试脚本的实际结果。
2. **实现事实源**：版本头、枚举定义、公共头文件、测试注册表。
3. **现行规范文档**：语言标准、编译器标准——它们描述**目标**，不是实现现状。
4. **设计文档**：VM / AOT / Embed / libtc / CLI 详设——描述架构与契约。
5. **导航与知识库**：`AGENTS.md`、`.cursor/README.md`、`.cursor/rules/**`、`.cursor/skills/**`。
6. **过程性记录**：CHANGELOG、审计报告、整改台账、release-checklist——只代表当时状态，不得当作现状依据。

裁决规则：

- 描述「现在是什么」的文档/注释，必须以第 1、2 层为准。
- 描述「应该是什么」的规范，以第 3 层为准；实现落后时标注差距，而不是改规范。
- 低优先级文档与高优先级冲突时，改低优先级文档；若同一事实在多处重复，保留权威处，其余改为链接。
- 规范与实现冲突且看不出是「未落地」还是「实现缺陷」时：不擅自改任何一方，记入遗留问题并给出证据（文件:行）。

## 第 1 步：建立基线（只读）

1. 确认工作区状态，记录已有未提交改动，避免覆盖或混入无关修改：
   ```bash
   git status --short
   git branch --show-current
   git log --oneline -10
   ```
2. 确认当前版本与阶段，以代码为准：
   ```bash
   rg -n "TC_VERSION|TC_AOT_VERSION|VERSION_STRING" src
   ```
3. 确认现行文档集合与版本命名（不要凭记忆写死文件名）：
   ```bash
   ls docs
   sed -n '1,160p' docs/README.md
   ```
4. 确认测试与门禁入口，以脚本为准：
   ```bash
   sed -n '1,80p' scripts/run_tests.sh
   ls scripts/sync
   ```
5. 若仓库正处于版本迁移期（新旧规范/设计文档并存），先判定：哪份是**现行规范**、哪份是**历史版本**、哪些链接仍指向旧文件名。把判定结果写入最终报告。

## 第 2 步：圈定变更面

1. 查看上次收尾以来实现侧发生了什么：
   ```bash
   git log --oneline --since="<上次收尾提交>" -- src tests scripts CMakeLists.txt
   git diff --stat <上次收尾提交>..HEAD -- src tests scripts
   ```
   没有明确的「上次收尾提交」时，用最近一次 `docs:` / `chore:` 收尾提交，或最近一个版本节点。
2. 从变更中提取需要同步的事实：新增/删除的模块、符号、错误码、CLI 选项、测试用例、版本号、目录结构。
3. 扫描陈旧与冲突线索（按需调整模式，勿机械替换）：
   ```bash
   rg -n "0\.0\.[0-9]+" --glob '*.md' --glob '*.mdc' --glob '*.h' --glob '*.c'
   rg -n "TODO|FIXME|XXX|待定|待实现|暂未|尚未|已废弃|deprecated|旧版|legacy" docs src .cursor README.md AGENTS.md
   ```
   重点核对：旧文件名/旧章节号、已删除符号、已改名命令与选项、已下线特性、失效的相对链接。
4. 对每个疑似问题记录：位置、现状、事实源、拟处理方式（改/删/标注/留待确认）。

## 第 3 步：文档分层扫描

按层处理，避免「全仓通读」；每份文档只核对与其职责相关的事实。

| 层级 | 文档 | 必查内容 |
|------|------|----------|
| 入口 | `README.md` / `README.en.md` | 版本、特性清单、构建与测试命令、目录树、示例可运行 |
| 代理导航 | `AGENTS.md`、`.cursor/README.md` | 版本、入口路径、命令、Skill/规则索引、链接 |
| 文档地图 | `docs/README.md` | 文档清单、版本、职责、已删除/新增文档 |
| 规范 | 现行语言标准、编译器标准 | 语法/语义与实现的可观察行为、错误码、章节交叉引用、附录计数 |
| 设计 | VM / AOT / Embed / libtc / CLI 详设 | 模块边界、调用链、数据结构、CLI 选项、诊断、版本 |
| 过程 | CHANGELOG、审计报告、整改台账、release-checklist | 只核对「当前状态」表述；历史条目保留并加取代注记 |
| 知识库 | `.cursor/skills/**`、`.cursor/rules/**` | 路由、符号名、测试规模、易错点、命令 |

逐项检查：

- [ ] 版本号、阶段/里程碑状态与代码一致。
- [ ] 文件路径、模块名、函数/类型/枚举名与 `src/` 一致。
- [ ] CLI 选项、默认值、退出码与 `main.c` / 帮助文本一致。
- [ ] 错误码名称、数量、诊断阶段与 `TcErrorKind`、`errors.md`、测试一致。
- [ ] 测试数量、用例名、注册入口与 `scripts/**/run_tests.sh`、`test-map.md` 一致。
- [ ] 示例代码可编译/可运行；输出与当前实现一致。
- [ ] Markdown 相对链接与锚点有效；被改名/删除的文档不再被引用。
- [ ] 设计文档不引用过程性文档（`check_doc_layering.py` 的规则）。
- [ ] 双语文件（`*.md` 与 `*.en.md`）事实同步，不出现一边更新一边过期。
- [ ] 规范领先实现之处显式标注「待落地」，并给出对应章节或跟踪项。

## 第 4 步：代码注释扫描

范围：`src/**/*.c`、`src/**/*.h`，必要时 `scripts/**`、`tests/**` 中的说明性注释。

- [ ] 文件头注释：模块职责、所属层、对外契约仍准确；无旧模块名/旧路径。
- [ ] 函数注释：参数、返回值、所有权、失败行为、副作用与实现一致；无「说 A 做 B」。
- [ ] 枚举/结构体/字段注释：语义、单位、取值范围、不变量与定义一致。
- [ ] 行内注释解释「为什么」，不解释显而易见的「做什么」；删除复述代码的噪音。
- [ ] 删除对已删除函数、变量、分支、文件的引用；删除被注释掉的死代码及其说明。
- [ ] `TODO` / `FIXME` / `XXX`：已解决则删除；仍有效则补上下文（问题、触发条件、关联测试或 issue）。
- [ ] 「临时」「兼容」「workaround」类注释：确认仍然成立，否则改写或删除。
- [ ] 注释中的版本号、错误码、默认值、上限与代码常量一致。
- [ ] 公共头文件注释与 `tc_*.h` ↔ `tc_*.c` 的实际签名一致。
- [ ] 注释风格符合 `.cursor/rules/coding-standards.mdc`：`/* ... */`、4 空格、无行尾空白；不做无关格式化。

约束：本步骤**只改注释**。若发现注释暴露了实现缺陷，不要改代码掩盖，记入遗留问题。

## 第 5 步：清理与裁决

对第 2–4 步收集的问题逐条处理，遵循：

1. **过时** → 改为当前事实；无保留价值的整段删除。
2. **错误** → 以事实源为准改正，并在报告中说明原错误与依据。
3. **冲突** → 按事实优先级保留一处权威表述，其余改为「见 ……」；禁止两处各说一套。
4. **重复** → 合并到单一事实源，其他位置只留链接。
5. **无法确认** → 不猜、不删；保留原文，列入「遗留问题」，注明需要谁/什么证据来裁决。
6. **历史记录** → 不改写过去条目；如过去结论已被推翻，追加「后续：已由 <提交/文档> 取代」。
7. **生成物/临时文件** → 仅清理确认由本仓库工具生成、且已被 `.gitignore` 覆盖的产物；不碰用户文件。

清理后再次全局搜索旧事实，确认没有残留：

```bash
rg -n "<被替换的旧版本号|旧文件名|旧符号名>" .
```

## 第 6 步：验证门禁

按改动范围选择，**不能只看文档自洽**：

```bash
# 静态一致性（必跑）
python3 scripts/sync/check_rhs_coverage.py
python3 scripts/sync/check_source_naming.py
python3 scripts/sync/check_doc_counts.py
python3 scripts/sync/check_doc_layering.py
python3 scripts/sync/check_section_refs.py
python3 scripts/sync/check_type_fact_source.py

# 空白/补丁完整性
git diff --check

# 相关测试（改动涉及行为描述、示例、测试清单时）
bash scripts/run_tests.sh --filter <相关用例名>

# 涉及代码或大范围文档改动时，跑全量
bash scripts/run_tests.sh
# 或完整本地 CI
bash scripts/ci.sh
```

要求：

- 门禁脚本若自身仍硬编码旧文件名/旧计数（迁移期常见），**先修脚本再跑**，不能以「脚本过期」为由跳过。
- 记录每条命令的退出码与关键输出；失败必须定位到具体文件:行。
- 若失败是本次改动引入的，修到通过；若确认是既存问题，在报告中单独标注「既存失败」，不得声称全部通过。
- 纯文档/注释改动至少保证：静态门禁全过 + `git diff --check` 干净 + 链接可解析。
- 构建或测试若因环境缺少依赖无法运行，明确写出缺失项与未验证范围。

## 第 7 步：输出收尾报告

按以下结构汇报，证据到文件:行：

```markdown
## 收尾基线
- 版本 / 提交：
- 现行规范文档：
- 上次收尾提交：
- 工作区初始状态：

## 改动清单
### 文档
- <文件>: <改了什么、为什么>
### 代码注释
- <文件>: <改了什么、为什么>
### 脚本 / 导航
- <文件>: <改了什么、为什么>

## 冲突裁决记录
| 冲突点 | 各方说法 | 裁决依据 | 处理 |
|--------|----------|----------|------|

## 验证结果
| 门禁/测试 | 结果 | 备注 |
|-----------|------|------|

## 遗留问题
- <文件:行>：<问题>；需要 <证据/决策>；未擅自修改的原因。

## 提交建议
- 建议信息：`docs: ...` / `chore: ...`
- 是否已提交：是/否
```

## 完成定义（全部满足才可称「收尾完成」）

- [ ] 全文搜索不到指向已删除/已改名文件、符号、章节的引用。
- [ ] 版本号、错误码数量、测试规模、CLI 选项在所有出现处一致，且与事实源一致。
- [ ] 规范领先实现的部分均有「待落地」标注，没有被描述成已实现。
- [ ] 代码注释与实际签名、返回值、失败行为一致；无死代码注释与过期 TODO。
- [ ] 设计文档未引用过程性文档；过程文档未冒充现状。
- [ ] 静态门禁全部通过；相关测试通过，或失败已被证明为既存并记录。
- [ ] 没有无关的代码语义改动、没有混入生成物、没有覆盖用户改动。
- [ ] 收尾报告已给出，遗留问题可执行、可追踪。
