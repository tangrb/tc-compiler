## 1. 目标

在不修改两份《TC 语言标准设计说明书》的前提下，重构 `docs/` 中其余六份文档，使它们共同表达以下三类事实，且不相互混淆：

1. TC 0.0.31 已经确定的语言规范；
2. v0.0.26 代码和可执行文件当前已经交付的行为；
3. 从 v0.0.26 达到 0.0.31 所需的设计变更、实现差距和验收条件。

重构后的文档既要能直接指导 0.0.31 实现，也要保证当前用户查阅 CLI 和 libtc API 时不会把尚未交付的能力当成现状。

## 3. 统一信息模型

### 3.1 三种状态

六份文档统一使用以下状态，不再用模糊的“当前版本”同时指代规范与实现：

| 状态 | 含义 | 允许的表述 |
| ---- | ---- | ---------- |
| **规范要求** | 0.0.31 标准的强制可观察语义 | “0.0.31 要求”“符合实现必须” |
| **目标设计** | 为满足规范而确定的 VM/AOT/libtc 内部设计 | “0.0.31 目标设计”“待实现/待验证” |
| **当前实现** | 仓库 v0.0.26 已交付并有测试证据的事实 | “v0.0.26 已实现”“当前命令/API” |

所有设计文档首页同时列出“规范基线 0.0.31”和“实现基线 v0.0.26”。任何 0.0.31 新能力都不得标成“已实现”。

### 3.2 冲突处理

1. 语言合法性、结果、错误分类和诊断阶段以 0.0.31 标准为准。
2. CLI 选项、公共函数签名、当前版本号和当前测试数量以 v0.0.26 代码/脚本为准。
3. 当前代码与 0.0.31 不一致时，设计文档描述目标方案，参考文档描述现状，合规报告登记差距。
4. 内部类型名、枚举名或函数名若尚未存在，必须标为“建议/目标设计”，不得伪装成当前符号。
5. 版本历史保留为附录；正文只围绕当前实现和 0.0.31 目标组织，不继续按 0.0.24、0.0.25、0.0.26 逐层叠加补丁章节。

### 3.3 链接规则

- 0.0.31 规范引用统一链接到 `TC语言标准设计说明书_0.0.31.md`。
- 当前实现事实可引用源文件、测试脚本和历史非版本化标准，但必须显式写明 v0.0.26。
- 删除指向不存在的开发计划文件或已删除快照的链接。
- 六份文档之间按职责交叉引用，避免复制整段规范正文。

## 4. 0.0.31 跨模块设计基线

三份目标设计文档必须一致覆盖以下变化。

### 4.1 语句与控制流

- 新增结构化 `while <bool_rhs> then ... end`。
- 新增仅作用于最内层 `while` 的 `break` 和 `continue`。
- `while` 块内禁止 `goto` 和 `label`，分别产生 `GotoInsideLoop`、`LabelInsideLoop` 静态错误。
- `goto` 继续只允许平级或向祖先作用域跳转；跳入子块、兄弟块仍非法。
- `if`、`while`、`break`、`continue`、`goto` 和短路边共同进入统一 CFG。
- `var` 唯一合法定义形态为 `var <name>: <type> = <rhs>`；缺少初始化器使用独立错误 `VarMissingInitializer`。
- 每个词法 `var` 绑定使用固定槽位；反向跳转或下一次循环迭代再次执行定义时，重新初始化同一槽位。

### 4.2 确定初始化

- 以 CFG 固定点分析取代只针对 `goto` 的局部源序近似。
- 会合点使用全部可达前驱 `OUT` 集合的交集。
- 循环条件失败、正常回边、`continue` 和 `break` 都是显式 CFG 边。
- 仅由字面量和源序中更早 `let` 组成的合法条件可以在编译期剪除不可能边。
- 不可达语句仍进行词法、语法、名称和类型检查，但不进入确定初始化前驱交集。
- 读取、赋值目标和 `read` 目标若不能在当前点证明已初始化，统一产生 `UninitializedVariable`。

### 4.3 RHS、数值语义与常量求值

- 新增等位宽、保持位模式的 `bitcast`；`bool` 不参与，不等宽产生 `BitcastWidthError`。
- `truncate` 仅用于整数窄化，不再承担整数/浮点位重解释。
- 严格 `cast` 对所有数值转换统一做目标可表示性检查；转换失败统一映射到 `CastOverflow` 或常量阶段的 `ConstantCastOverflow`。
- 浮点 `wrap` 删除；浮点仅支持严格模式和显式 `ieee` 模式。
- 浮点逐操作按目标精度舍入，固定异常优先级和 NaN 行为；VM、AOT 和 `let` 求值必须一致。
- `let` 只允许原子或单个非嵌套调用，且每一步按声明类型和运行时相同模式求值。

### 4.4 诊断与非语言错误

- 0.0.31 权威枚举为 41 个语言错误码，加 1 个实现扩展 `OutOfMemory`。
- 新增或恢复 `VarMissingInitializer`、`UninitializedVariable`、`BitcastWidthError`、`LabelInsideLoop`、`GotoInsideLoop`、`BreakOutsideLoop`、`ContinueOutsideLoop`。
- 删除 `GotoSkipsVarInit`、`OverflowMode`、`ConstantCircular`、`FloatCastOverflow` 和 `CrossBlockReference` 等旧分类；按 0.0.31 统一映射。
- REPL 限制、文件打开失败和 OOM 属于实现/API 边界，不得写成 TC 批量源文件的语言语法错误。
- TC 0.0.31 不定义编译警告。

## 5. 逐文档重构设计

### 5.1 TC-VM 详细设计说明书

正文重排为“边界与状态 → 流水线 → IR/AST → 解析与作用域 → CFG/Analyzer → Executor → 数值与 I/O → 诊断 → REPL → 验证”。主要设计如下：

- 在语句表示中增加 `WhileStmt`、`BreakStmt`、`ContinueStmt` 的目标变体，并在 RHS 表示中增加 `BitcastRhs` 目标变体。
- 将仅围绕 `if` 的缩进解析说明提升为通用块解析模型，统一 `if`/`else`/`while`/`end` 的缩进栈规则。
- 把标签解析、块路径和循环祖先信息纳入词法作用域模型。
- 单设 CFG 构建与固定点分析章节，明确节点、边、入口集合、交集会合、常量边剪枝和诊断时机。
- Executor 以结构化执行帧或等价指令指针目标表达 `while` 条件、回边、`break` 出口和 `continue` 目标；不得用宿主递归语义掩盖可观察差异。
- 数值章节按 0.0.31 重写浮点模式、严格转换、整数窄化和 `bitcast`。
- REPL 章节明确其多行限制是实现策略，不是语言规范。
- 当前 v0.0.26 的模块、测试数和已有行为集中放入“实现基线”与历史附录，不混入目标设计结论。

### 5.2 TC-AOT 详细设计说明书

正文重排为“边界与状态 → 输入契约 → C99 代码生成 → shim/数值语义 → 诊断边界 → 差分验证”。主要设计如下：

- Analyzer 在进入 AOT 前完成名称、类型、范式隔离和完整 CFG 确定初始化；AOT 只接收已验证的 typed program。
- `while` 生成原生 C `while` 或语义等价的显式标签结构；`break`/`continue` 必须落到最内层目标。
- 词法变量槽在函数/程序作用域顶部固定声明；每次执行 TC `var` 都重新写入同一槽，保持循环和反向跳转语义。
- `goto`/`label` 继续生成唯一 C 标签，但仅对 Analyzer 已判定合法的控制流发射。
- `bitcast` 通过 `memcpy` 或等价的 C99 无别名违规方案实现，不使用会触发未定义行为的指针强转。
- 严格 `cast`、浮点异常/舍入、NaN 和 `let` 常量折叠与 VM 共享语义函数或共享明确契约；删除浮点 `wrap` 目标路径。
- 差分测试按语言正例、静态拒绝、运行时错误和位模式一致性分组；只有实现与验证完成后才能把版本状态改为已交付。

### 5.3 libtc 设计说明书

正文重排为“公共边界 → 编译流水线 → 数据模型与所有权 → 诊断契约 → VM/AOT 消费关系 → 兼容性”。主要设计如下：

- 现有公共 API 签名在目标设计中保持不变；0.0.31 变化由解析、typed program、Analyzer 和语义层吸收。
- `TcTypedProgram` 的目标数据契约增加结构化循环、控制转移、CFG/作用域元数据或其可重建信息。
- 明确 AST/typed IR 中新增节点的递归释放、失败回滚和 OOM 传播责任。
- `tc_compile_source`/`tc_compile_file` 在返回成功前完成 0.0.31 全部静态检查；`tc_run_typed` 只处理运行时语义错误。
- 诊断单槽继续 fail-fast，但错误阶段和打印名按 0.0.31 映射；文件读取和 OOM 仍属于实现错误。
- 将 v0.0.24～v0.0.26 的增量章节压缩为兼容历史，新增清晰的“0.0.31 目标影响”章节。

### 5.4 TC-VM 命令行参考

该文档不改写成尚未存在的 0.0.31 用户手册：

- 首页明确命令版本为 v0.0.26，所有命令输出、选项、退出码和示例均以当前二进制为准。
- 现有 0.0.26 支持的 `if`、浮点和受限 `goto` 保持为当前行为。
- 不把 `while`、`break`、`continue`、`bitcast` 或新错误名列为当前可用能力。
- 新设“0.0.31 规划边界”章节，概述未来语言能力、仍不变的 CLI 入口以及当前不可用状态。
- 错误表拆成“当前 v0.0.26 可输出错误”和“0.0.31 目标错误迁移”，避免混表。
- REPL 限制明确标成 tc-vm 的交互实现策略。

### 5.5 libtc API 速查

- 保持为 v0.0.26 可调用 API 的短文档，函数签名、返回值、所有权和示例必须与当前头文件一致。
- 首页增加“规范 0.0.31 / 实现 v0.0.26”双基线提示。
- 新设“0.0.31 兼容性预期”，说明目标设计不增加公共函数，但编译接受集、诊断种类和 typed program 内部内容将变化。
- 新错误枚举和新语句/RHS 类型只能放在目标说明中，不得标成当前头文件已经提供。
- 与 `libtc设计说明书.md` 分工：速查只保留调用者需要的信息，内部流水线和目标结构链接到设计说明书。

### 5.6 设计实现合规审查报告

报告改为两个相互独立的结论区：

1. **v0.0.26 已实现合规基线**：保留 375/375、384 VM、857 unit、210 AOT 等既有历史证据，并明确这些数字只证明 v0.0.26。
2. **0.0.31 规范差距**：明确当前实现不得声明 0.0.31 合规，按 parser、types/IR、scope、CFG/analyzer、semantics/const-eval、executor、AOT、diagnostics、CLI/API 和 tests 列出差距。

0.0.31 部分不虚构新的完成项总数或通过率。在代码与测试尚未交付时，状态只使用“未实现”“部分基础可复用”“待验证”。最终合规门槛包括：

- 全部 0.0.31 语法与语义已实现；
- VM/AOT/常量求值在数值和控制流上行为一致；
- 42 个规范/扩展错误码按阶段映射；
- 正例、静态错误、运行时错误、CFG、循环、bitcast 和迁移回归齐备；
- 全量测试、覆盖检查、命名检查和差分测试通过；
- 六份文档中的“待实现”状态与实际代码同步更新。

## 6. 编辑原则

- 优先整体重排当前章节，而不是在文末继续堆叠版本补丁。
- 规范规则只摘要并链接原文；实现设计解释数据结构、流水线和边界。
