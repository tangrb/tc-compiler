## P4-01：tc_parser.c 模块拆分

### 现状

`src/vm/parser/tc_parser.c` 共 **2,093 行**，容纳了：
- 行收集与 `tc_parse_source_to_program`
- 16 种 RHS 的 `tc_parse_rhs` / `tc_parse_const_rhs`
- 9 种语句的 `tc_parse_statement`
- if 多行解析 + 缩进引擎（R1–R6）
- `tc_rhs_free` / `tc_statement_free` / `tc_program_push`
- 辅助函数（`tc_operand_free` 等）

这是项目中最大的源文件，且功能高度内聚度低（缩进状态机 ≠ RHS 释放逻辑）。

### 目标

| 新文件 | 职责 | 预估行数 |
|--------|------|---------|
| `src/vm/parser/tc_parser.c`（保留） | `tc_parse_source_to_program`、缩进引擎、`tc_parse_if_stmt` | ~800 |
| `src/vm/parser/tc_parser_rhs.c` | `tc_parse_rhs`、`tc_parse_const_rhs`，辅助类型检查 | ~600 |
| `src/vm/parser/tc_parser_free.c` | `tc_rhs_free`、`tc_statement_free`、`tc_operand_free`、`tc_program_free` | ~300 |
| `src/vm/parser/tc_parser.h`（扩展现有） | 新增函数声明（非 static 化必要的函数） | — |

### 改动清单

| # | 改动 | 文件 | 风险 |
|---|------|------|------|
| 1 | 将 `tc_parse_rhs`、`tc_parse_const_rhs`、`tc_parse_and_or_not_rhs`、`tc_parse_bitwise_bin_rhs`、`tc_parse_shift_rhs`、`tc_parse_cast_rhs` 移出并暴露声明 | `tc_parser.c` → `tc_parser_rhs.c` + `tc_parser.h` | 中：需验证所有 static 函数引用 |
| 2 | 将 `tc_rhs_free`、`tc_statement_free`、`tc_operand_free`、`tc_program_push`、`tc_program_free`、`tc_program_init` 移出 | `tc_parser.c` → `tc_parser_free.c` + `tc_parser.h` | 低：纯释放逻辑，无状态依赖 |
| 3 | 更新 `CMakeLists.txt` 添加新文件 | `src/vm/CMakeLists.txt` | 低 |
| 4 | 更新 `check_source_naming.py` 白名单 | `scripts/sync/check_source_naming.py` | 低 |
| 5 | 更新知识图谱 `tc_rhs_free`/`tc_statement_free` 行号 | `.cursor/rules/knowledge-graph.mdc` | 低 |
| 6 | 更新 `features.md` 符号位置行号 | `.cursor/skills/tc-architecture/features.md` | 低 |
| 7 | 全量回归（VM + AOT + unit） | `make test` | — |

### 依赖

- `tc_parser_rhs.c` 无前置依赖
- `tc_parser_free.c` 无前置依赖
- 两者可并行实施

### 工时估计

4–6 小时（含验证）

## P4-02：tc_semantics.c 子模块拆分

### 现状

`src/vm/runtime/tc_semantics.c` 共 **1,814 行**，容纳了：
- 位模式工具（`tc_mask_bits`、`tc_bits_to_signed` 等）
- 字面量检查（`tc_literal_fits_type`、`tc_literal_to_value`）
- 整数双目/单目算术
- 比较运算
- 类型转换（含 truncate 位重解释）
- 位运算（`tc_exec_bitwise_binary` / `tc_exec_bitwise_unary`）
- 移位（`tc_exec_shift`）
- 浮点算术/比较/cast（3 模式）
- 未初始化哨兵定义

逻辑上可分为 3 个内聚子域：整数、浮点、位运算。

### 目标

| 新文件 | 职责 | 预估行数 |
|--------|------|---------|
| `src/vm/runtime/tc_semantics.c`（保留） | 共享工具函数、字面量检查、未初始化哨兵 | ~400 |
| `src/vm/runtime/tc_sem_int.c` | 整数算术（add/sub/mul/div/mod/abs/neg）、整数 cast | ~500 |
| `src/vm/runtime/tc_sem_fp.c` | 浮点算术/比较/cast（strict/ieee/wrap 三模式） | ~500 |
| `src/vm/runtime/tc_sem_bitwise.c` | 位运算（and/or/xor/not）、移位（shl/shr） | ~300 |
| `src/vm/runtime/tc_semantics.h`（扩展现有） | 新增函数声明 | — |

### 改动清单

| # | 改动 | 文件 | 风险 |
|---|------|------|------|
| 1 | 拆分整数算术函数到 `tc_sem_int.c` | `tc_semantics.c` → `tc_sem_int.c` + `tc_semantics.h` | 中：依赖 `tc_mask_bits`、`tc_value_make` 等工具函数 |
| 2 | 拆分浮点函数到 `tc_sem_fp.c` | `tc_semantics.c` → `tc_sem_fp.c` | 中：需暴露位模式底层工具 |
| 3 | 拆分位运算/移位到 `tc_sem_bitwise.c` | → `tc_sem_bitwise.c` | 低：相对独立 |
| 4 | 更新 `src/vm/CMakeLists.txt` | CMake 添加新 `.c` | 低 |
| 5 | 更新 `src/vm/runtime/CMakeLists.txt`（unit tests） | 将新文件加入 link | 低 |
| 6 | 更新 8 个单元测试文件的 `#include` | `tests/unit/runtime/*.c` | 低：头文件接口不变 |
| 7 | 更新 `tc_aot_rt.c` 的 `#include` | `src/aot/tc_aot_rt.c` | 低 |
| 8 | 更新 `tc_io.c` 的 `#include` | `src/vm/runtime/tc_io.c` | 低 |
| 9 | 更新 `tc_executor.c` 的 `#include` | `src/vm/executor/tc_executor.c` | 低 |
| 10 | 全量回归 | `make test` | — |

### 关键问题

是否将工具函数（`tc_mask_bits`、`tc_value_make`、`tc_bits_to_signed` 等）保留在 `tc_semantics.c` 还是抽到独立 `tc_sem_util.c`？

**建议**：保留在 `tc_semantics.c`（非 static 化），其余子模块 `#include "tc_semantics.h"` 并链接同一 `.o`。因这些工具函数变更频率低，不必过度拆分。

### 工时估计

6–8 小时（含验证）

## P4-03：tc_analyzer.c 按 Pass 拆分

### 改动清单

| # | 改动 | 文件 | 风险 |

| 3 | 拆分数据流分析 | → `tc_analyzer_dfa.c` | 中：`TcInitState` 类型定义改动 |
| 4 | 拆分 REPL 分析 | → `tc_analyzer_repl.c` | 低：相对独立 |
| 5 | 更新 `src/vm/CMakeLists.txt` | 添加新 `.c` | 低 |
| 6 | 更新 `tests/unit/runtime/test_analyzer.c` 的链接配置 | `tests/unit/runtime/CMakeLists.txt` | 低 |
| 7 | 更新知识图谱 `tc_analyzer.c` 行号 | `.cursor/rules/knowledge-graph.mdc` | 低 |

数据流系统与 Pass2 共享状态（`TcInitState` 的 per-slot 数组），拆分时需确定：

## P5-01：tc_stmt_index.c 内联评估

### 现状

独立模块 `src/vm/runtime/tc_stmt_index.c`（43 行）+ `tc_stmt_index.h`（声明），包含 4 个函数：
- `tc_stmt_index_reset` / `tc_stmt_index_take`（各 5–6 行）
- `tc_stmt_block_index_span` / `tc_stmt_subtree_index_count`（各 10–14 行）
- `tc_stmt_index_skip_block`（3 行）

### 选项

| 选项 | 优点 | 缺点 |
|------|------|------|
| **A（保持现状）** | 模块边界清晰，OOM 安全有独立文档 | 额外文件管理开销 |
| **B（内联到 `tc_parser.c` + `tc_parser.h`）** | 减少 1 个模块 | 使用方（executor/aot 等）需 include parser.h |
| **C（改为仅头文件 `tc_stmt_index.h`）** | 零编译管理，inline 优化 | 需标记 `static inline`；`tc_stmt_subtree_index_count` 递归不变 |

### 建议

**选项 C**，原因：
- 函数体极小（无循环/递归外部依赖）
- `tc_stmt_subtree_index_count` 递归体内使用 `tc_stmt_block_index_span` 没问题
- 消除 CMake + 知识图谱中 1 对文件

### 改动清单

| # | 改动 | 文件 | 风险 |
|---|------|------|------|
| 1 | 将 `tc_stmt_index.c` 内容搬至 `tc_stmt_index.h` 末尾 | 删除 `.c`，编辑 `.h` | 低：需加 `static inline` |
| 2 | 删除 `tc_stmt_index.c` | — | 低 |
| 3 | 更新 `src/vm/CMakeLists.txt` | 移除 `.c` 引用 | 低 |
| 4 | 更新 4 个使用方的 `#include` | `tc_analyzer.c` / `tc_executor.c` / `tc_aot_codegen.c` / `test_stmt_index.c` | 低 |
| 5 | 更新 `check_source_naming.py` 白名单 | 移除 | 低 |
| 6 | 更新知识图谱 | `.cursor/rules/knowledge-graph.mdc` | 低 |

### 工时估计

1 小时

## P5-02：tc_warning.c 清理决策

### 现状

`src/vm/runtime/tc_warning.c`（65 行）+ `tc_warning.h`（声明），仅含：
- `tc_warning_list_init` / `tc_warning_list_free` / `tc_warning_list_add` / `tc_warning_list_print`
- 警告枚举仅有 `TC_WARN_NONE`（占位）
- 单元测试 `test_warning.c`（59 用例）

v0.0.26 已将 `TC_WARN_UNINITIALIZED_VARIABLE` 升级为错误，当前无活跃警告种类。

### 选项

| 选项 | 优点 | 缺点 |
|------|------|------|
| **A（保持空壳）** | 为将来警告类型提供基础设施 | 空壳，无实际用途 |
| **B（保持并标记 deprecated）** | 同上 + 清晰信号 | 文件仍然存在 |
| **C（删除）** | 减少代码量 | 未来加警告需重写基础设施 |

### 建议

**选项 B**：在文件顶部添加注释标记 "deprecated — no active warning kinds"，保留基础设施和单元测试。理由是语言编译器始终可能引入新警告（如未使用变量、不可达代码），保留骨架可降低未来启动成本。

### 改动清单

| # | 改动 | 文件 | 风险 |
|---|------|------|------|
| 1 | `tc_warning.h` 顶部添加 `@deprecated` 注释 | `tc_warning.h` | 无 |
| 2 | `tc_warning.c` 顶部添加 `@deprecated` 注释 | `tc_warning.c` | 无 |

### 工时估计

15 分钟

## 执行路线图

### 推荐顺序

```
M1 [快速见效] → P5-02 空壳标记 + P5-03 归类 (30min)
M2 [核心重构] → P4-01 parser 拆分 (4-6h)
```


### 风险控制

- P4-02（semantics 拆分）：影响 executor 和 AOT，需确认 `#include` 和链接顺序正确
- P4-03（analyzer 拆分）：数据流系统与 Pass2 紧耦合，推荐**先拆分 Pass1 和 REPL**（低风险），**后拆分 Pass2 + 数据流**
