## 优先级定义

| 级别 | 含义 |
|------|------|

## P0 — 高优先级

### 1. 拆分 Analyzer

**问题**：`src/vm/analyzer/analyzer.c` 1,117 行，同时承载：
- Pass1 符号收集（`tc_pass1_collect_symbols`）
- Pass2 类型检查（`tc_pass2_type_check` / `tc_check_rhs`）
- let 编译期常量求值（`tc_eval_const_rhs` / `tc_eval_const_operand` / `tc_resolve_const_value`）
- 警告系统

**建议**：将常量求值逻辑（预估 ~400 行）提取为独立的 `src/vm/analyzer/const_eval.c`，保持 pass1/pass2 聚焦符号与类型检查。

**涉及文件**：
- `src/vm/analyzer/analyzer.c`
- `src/vm/analyzer/tc_analyzer.h`（可能需要新增头文件）

---

### 2. Parser 递归深度保护

**问题**：`tc_parse_rhs` 和 `tc_parse_const_rhs` 递归解析表达式时无深度限制。深层嵌套的复杂表达式（如多层嵌套算术/比较/逻辑）可能导致 C 栈溢出。

**建议**：在 parser 上下文中增加递归深度计数器（如 `TcParserCtx.depth`），每次进入 `tc_parse_rhs` / `tc_parse_const_rhs` 递增，超过阈值（如 256）返回 `TC_ERR_SYNTAX`，并附带诊断信息"expression too complex"。

**涉及文件**：
- `src/vm/parser/parser.c`（`TcParserCtx` 结构体）
- `src/vm/parser/tc_parser.h`（如定义在头文件中）

### 4. OOM 审计

**问题**：部分 `malloc` / `calloc` 失败路径返回 `-1` 并设置诊断，但部分分配点未明确处理 OOM 场景，存在未定义行为风险。

**建议**：全局审计所有动态内存分配点：
1. 搜索 `malloc` / `calloc` / `realloc` 调用，确认每个失败路径都：
   - 返回 `-1`（或合适的错误码）
   - 调用 `tc_diagnostic_set(diag, TC_ERR_SYNTAX, ...)` 设置诊断
   - 不继续使用 NULL 指针
2. 考虑引入 `tc_malloc` / `tc_calloc` 包装函数统一 OOM 处理

**涉及文件**：
- `src/vm/parser/parser.c`
- `src/vm/analyzer/analyzer.c`
- `src/vm/executor/executor.c`
- `src/vm/runtime/symbol.c`
- `src/aot/tc_aot_codegen.c`

**实施记录**（2026-07-04）：
- **`parser.c` `tc_program_push`**: 添加 `TcDiagnostic *diag` 参数，OOM 时调用 `tc_diagnostic_set` 设置诊断；同步更新 `tc_parser.h` 声明和 `compile.c` 调用点
- **`lexer.c` `tc_token_list_push`/`tc_emit_token`**: 添加 `TcDiagnostic *diag` 参数链，OOM 时调用 `tc_diagnostic_set` 设置诊断（扩展审计发现）
- **`analyzer.c`**: `last_init` malloc 已有诊断 ✅
- **`executor.c`**: `slots` malloc 已有诊断 ✅
- **`symbol.c`**: `realloc` + `strdup` 均有诊断 ✅
- **`compile.c`**: 两处 malloc 均有诊断 ✅
- **`repl.c`**: 两处 realloc 均有诊断 ✅
- **`aot/main.c`**: malloc 返回 NULL，调用侧已处理 ✅
- **`warning.c` `tc_warning_list_add`**: OOM 仅返回 -1 无诊断 —— **有意为之**（警告系统为 best-effort，不阻断编译，缺失警告可接受）
- **`diagnostic.c`**: `strdup` 失败 → 字段为 NULL，`tc_diagnostic_print` 通过 `?: ""` 和 `!line_text` 安全处理 ✅
- **`aot/tc_aot_codegen.c`**: 无动态分配 ✅

## P2 — 低优先级

### 5. 统一 I/O 实现 ✅

**问题**：`read` / `write` 在 `executor.c` 和 `tc_aot_rt.c` 中有两份平行实现，增加了维护负担和测试不一致风险。

**解决**：
1. 将 I/O 逻辑提取为共享函数 `src/vm/runtime/tc_io.c` / `tc_io.h`
2. `executor.c` 和 `tc_aot_rt.c` 都委托该共享实现
3. 编写了针对共享 I/O 函数的单元测试（20 个用例，覆盖所有格式符和边界值）

**涉及文件**：
- `src/vm/runtime/tc_io.c`（新建）
- `src/vm/runtime/tc_io.h`（新建）
- `src/vm/executor/executor.c`（删除 ~300 行重复代码）
- `src/aot/tc_aot_rt.c`（删除 ~220 行重复代码）
- `src/aot/main.c`（编译命令加入 tc_io.c）
- `src/libtc/CMakeLists.txt`（加入 tc_io.c）
- `tests/unit/runtime/test_io.c`（新建单元测试）
- `tests/unit/runtime/CMakeLists.txt`（注册 check-io）
- `tests/CMakeLists.txt`（check-io 加入 check-unit）

**实施记录**（2026-07-04）：
- 合并 `tc_write_formatted`、`tc_exec_write_value`（executor.c）和 `tc_aot_write`（tc_aot_rt.c）为 `tc_io_write_formatted` + `tc_io_write_value`
- 合并 `tc_io_skip_whitespace`、`tc_read_decimal_digits`（executor.c）和 `tc_aot_skip_whitespace`、`tc_aot_read_decimal_digits`（tc_aot_rt.c）为 `tc_io_skip_whitespace` + `tc_io_read_digits`
- 合并 `tc_exec_io_read`（executor.c）和 `tc_aot_read`（tc_aot_rt.c）为 `tc_io_read_value`
- 共享版使用 `FILE *out` 参数（executor 版更通用，支持任意输出流），**保留 executor 版的 I/O 错误检查**（AOT 旧版遗漏了 fflush 返回值检查）
- 单元测试覆盖：%d/%i/%u/%x/%X/%o/%b/%t 格式、signed/unsigned/bool 类型、INT64_MIN/INT64_MAX/UINT64_MAX 边界、"true"/"false" bool 输出、newline 选项
- 所有 584 个测试（VM 198 + 单元 404 + AOT 22）全部通过 ✅
