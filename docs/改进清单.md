## 优先级定义

| 级别 | 含义 |
|------|------|
| **P0** | 必须尽快处理 — 影响正确性、稳定性或可维护性的严重问题 |
| **P1** | 应当处理 — 显著提升代码质量或测试覆盖，无紧急风险 |
| **P2** | 建议处理 — 提升工程基础设施或减少重复劳动 |

---

## P0 — 高优先级

### 1. 拆分 Analyzer

**问题**：`src/vm/analyzer/analyzer.c` 1,117 行，同时承载：
- Pass1 符号收集（`tc_pass1_collect_symbols`）
- Pass2 类型检查（`tc_pass2_type_check` / `tc_check_rhs`）
- let 编译期常量求值（`tc_eval_const_rhs` / `tc_eval_const_operand` / `tc_resolve_const_value`）
- 警告系统

**建议**：将常量求值逻辑（预估 ~400 行）提取为独立的 `src/vm/analyzer/const_eval.c`，保持 pass1/pass2 聚焦符号与类型检查。

**涉及文件**：
- `src/vm/analyzer/analyzer.c`
- `src/vm/analyzer/tc_analyzer.h`（可能需要新增头文件）

---

### 2. Parser 递归深度保护

**问题**：`tc_parse_rhs` 和 `tc_parse_const_rhs` 递归解析表达式时无深度限制。深层嵌套的复杂表达式（如多层嵌套算术/比较/逻辑）可能导致 C 栈溢出。

**建议**：在 parser 上下文中增加递归深度计数器（如 `TcParserCtx.depth`），每次进入 `tc_parse_rhs` / `tc_parse_const_rhs` 递增，超过阈值（如 256）返回 `TC_ERR_SYNTAX`，并附带诊断信息"expression too complex"。

**涉及文件**：
- `src/vm/parser/parser.c`（`TcParserCtx` 结构体）
- `src/vm/parser/tc_parser.h`（如定义在头文件中）

---

## P1 — 中优先级

### 3. 扩充单元测试

**问题**：目前仅 3 个 lexer 单元测试（`tests/unit/lexer/`），核心逻辑层缺乏细粒度单元测试覆盖。

**建议**：
1. 优先为 `src/vm/runtime/semantics.c`（872L，核心运算逻辑）编写全面单元测试
2. 为 `src/vm/runtime/types.c`（271L，类型工具函数）编写单元测试
3. 接入覆盖率工具（gcov/lcov）跟踪测试进度
4. 在 `make test` 中加入单元测试目标

**涉及文件**：
- `tests/unit/`（新建子目录如 `runtime/`）
- `tests/unit/CMakeLists.txt`（扩展构建配置）
- `Makefile`（如果单元测试构建未集成）

---

### 4. OOM 审计

**问题**：部分 `malloc` / `calloc` 失败路径返回 `-1` 并设置诊断，但部分分配点未明确处理 OOM 场景，存在未定义行为风险。

**建议**：全局审计所有动态内存分配点：
1. 搜索 `malloc` / `calloc` / `realloc` 调用，确认每个失败路径都：
   - 返回 `-1`（或合适的错误码）
   - 调用 `tc_diagnostic_set(diag, TC_ERR_SYNTAX, ...)` 设置诊断
   - 不继续使用 NULL 指针
2. 考虑引入 `tc_malloc` / `tc_calloc` 包装函数统一 OOM 处理

**涉及文件**：
- `src/vm/parser/parser.c`
- `src/vm/analyzer/analyzer.c`
- `src/vm/executor/executor.c`
- `src/vm/runtime/symbol.c`
- `src/aot/tc_aot_codegen.c`

---

## P2 — 低优先级

### 5. 统一 I/O 实现

**问题**：`read` / `write` 在 `executor.c` 和 `tc_aot_rt.c` 中有两份平行实现，增加了维护负担和测试不一致风险。

**建议**：
1. 将 I/O 逻辑提取为共享函数，放在 `src/vm/runtime/` 下
2. `executor.c` 和 `tc_aot_rt.c` 都委托该共享实现
3. 编写针对共享 I/O 函数的单元测试

**涉及文件**：
- `src/vm/executor/executor.c`
- `src/aot/tc_aot_rt.c`
- 新建：`src/vm/runtime/tc_io.c` / `src/vm/runtime/tc_io.h`

---

### 6. 接入持续集成

**问题**：项目无 CI 配置，测试需手动运行 `make && make test`，无法自动发现回归。

**建议**：
1. 创建 `.github/workflows/ci.yml`，配置 GitHub Actions
2. CI 步骤应包括：
   - `make` 编译（验证全部源码可编译）
   - `make test` 运行 VM 测试
   - `bash scripts/vm/run_tests.sh` 运行全部集成测试
   - `bash scripts/aot/run_tests.sh` 运行 AOT 测试
   - 单元测试构建与运行
3. 可选：在 CI 中运行覆盖率收集

**涉及文件**：
- `.github/workflows/ci.yml`（新建）
- `Makefile`（可能需要调整测试目标）

---

### 7. Stress 测试扩充

**问题**：目前仅 2 个 stress 测试（`many_operations.tc`、`massive_vars.tc`），大规模/边界场景覆盖不足。

**建议**：增加以下场景的 stress 测试：
- 深层递归表达式（如 `add(int32, add(int32, add(int32, ...)))`）
- 长链 let 依赖（`let a = 1; let b = add(int32, a, a); let c = ...` 连几十层）
- 大量 I/O 操作（连续写/读数百行）
- 大量变量的符号表压力测试
- 类型边界组合（所有类型跨所有运算符）

**涉及文件**：
- `tests/stress/`（新增 `.tc` 文件）
- `scripts/vm/run_tests.sh`（注册新测试）

---

### 8. 知识图谱自动化同步检查

**问题**：加新 `TcRhsKind` 需手动更新 8 个分发点和多份文档，无自动化验证。

**建议**：
1. 为 `knowledge-graph.mdc` 中的分发点表添加注释，标明每个分发点的文件/行号
2. 考虑编写一个简单的 bash 脚本或 Python 脚本，检查 `tc_parse_rhs`、`tc_parse_const_rhs`、`tc_rhs_free`、`tc_check_rhs`、`tc_eval_const_rhs`、`tc_eval_rhs`、`tc_aot_emit_rhs` 中各 `TC_RHS_` case 是否完整
3. 将检查脚本纳入 CI

**涉及文件**：
- `.cursor/rules/knowledge-graph.mdc`
- `scripts/`（新增检查脚本）

### 9. AOT 测试归属规范化

**问题**：AOT 测试脚本（`scripts/aot/run_tests.sh`）与 VM 测试脚本（`scripts/vm/run_tests.sh`）分离，特性变更时可能漏注册。

**建议**：
1. 统一测试注册入口，或至少确保 `run_tests.sh` 顶层入口同时触发两个子目录的测试
2. 在 `docs/` 中明确记录 AOT 测试注册流程

**涉及文件**：
- `scripts/run_tests.sh`（新建顶层入口或修改 Makefile）
